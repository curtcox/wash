# Chapter 1 — Getting Started

> *Draft.* This chapter assumes you are reading it the way the book is meant to
> be read: in a browser, served by `wash`, on your own machine. If you are
> reading it as plain text on a screen somewhere, the first thing to do is stop
> and start the live version — the rest of the chapter will make more sense, and
> a good deal of it you are supposed to *click*.

---

## 1.1 Read this in your browser

The shortest path into `wash` is to run the book.

```sh
git clone https://github.com/curtcox/wash
cd wash
./start
```

`./start` does two unremarkable things: it launches a small local web server
that serves the book's project directory, and it opens your browser to that
server's home page — a short console with a live box you will use in a moment,
and a link to this chapter. A moment later your browser is pointed at an address
something like:

```
http://localhost:8080/
```

Follow the **Chapter 1** link there and you arrive here, at an address like:

```
http://localhost:8080/render/ch01.md
```

That URL is worth a second look, and §1.2 is about exactly what it means.

That is the whole installation. There is no daemon to register, no account to
create, no cloud to reach. The server is talking only to you, only on your
machine, over a port only you can see. Everything in this book happens between
your browser and your own files.

> **Why a browser, and why local?**
> Kernighan and Pike wrote *The Unix Programming Environment* for people sitting
> at a terminal connected to a shared minicomputer. The terminal was a window
> onto programs and files. Forty years later almost everyone has a far more
> capable window already open all day — the browser — but we have been trained
> to point it at *other people's* computers. `wash` points it back at your own.
> The browser becomes the terminal; the URL becomes the command line; your
> filesystem stays exactly where it is.

A note on what we are *not* doing. `wash` is a single-user tool. There is no
login, no permission model beyond the one your operating system already gives
your own account, no attempt to be safe against a hostile network because there
is no network — just you and your files. If that sounds reckless, remember it is
the same trust model as your shell: when you type `rm` at a prompt, nothing asks
whether you are sure. We will lean on that freedom rather than apologize for it.

## 1.2 The first surprise: this page is a file

Before we do anything clever, look at what is already in front of you. You are
reading Chapter 1. The chapter is not generated by an application, not assembled
by a template engine, not pulled from a database. It is a single file on disk —
`ch01.md`, written in Markdown — and the URL in your address bar tells you so.

The address is `/render/ch01.md`. Read it as a tiny pipeline: take the file
`ch01.md` and run it through a command called `render`, which turns Markdown into
the HTML you are reading. Now delete the `/render/` prefix from your address bar,
leaving just:

```
/ch01.md
```

There is the raw Markdown source of the page you were reading a moment ago —
asterisks, backticks, and all. Same file, two views: `render` dressed it up;
asking for it plainly hands you the bytes. **A URL in `wash` is a path under the
project directory (optionally run through commands named on the left), and
asking for a path gives you what is there.**

This is the bedrock idea, so it is worth saying plainly:

```
GET /ch01.md            →   site/ch01.md          (the raw file)
GET /render/ch01.md     →   render < site/ch01.md  (the file, rendered)
```

The things on the left are requests your browser makes. The things on the right
are a file in the cloned repository, and a command run over it. That arrow is
almost the entire specification.

> **Try it.** Open a second tab and visit `/notebook/0/`. You will see a listing
> of what is inside that directory — because it has no index file, `wash` shows
> you the bare contents. The home page, by contrast, lives in a directory that
> *does* have an index file (`index.html`), so visiting `/` serves the page
> rather than a listing. Two behaviors, one rule, no configuration language.

## 1.3 The loop: type something, get a tree

Reading files is the quiet half of `wash`. The loud half is composition — making
the browser *do* things and keep the results. The fastest way to feel it is the
live box on the home console. Click **home** at the top of this page (it is on
every page), and you will find a text box with a **Send** button.

Type a question into the box — say `What is 2+2?` — and press **Send**.

Three things happen, and the URL bar tells the story. Your browser POSTs what you
typed; a command runs; and you land on a *page whose address did not exist a
moment ago*:

```
http://localhost:8080/view/notebook/0/0/0
```

That page shows the answer — `4` — under your question. Read the address as a
pipeline again: a command called `view`, run over the path `notebook/0/0/0`. And
that path is the interesting part. Walk it back one segment at a time:

```
notebook/0/0/0    the answer the command produced
notebook/0/0      your question, stored
notebook/0        the start of this notebook
notebook          the notebook itself
```

You did not name any of this. You typed a sentence and `wash` filed it. Ask a
second question and the next answer lands at `notebook/0/1/0`; the notebook grows
a numbered trail you can walk, bookmark, and share, because every step is just a
path you can address by URL.

> **The LLM is not special.** The command behind that box might call a language
> model, or it might run `wc`, or a three-line shell script. To `wash` they are
> the same kind of thing: a program that reads input and writes output. Swap the
> command and the same loop will file word counts, or shell results, or model
> answers, into the same kind of numbered trail. We will lean on this hard later;
> for now just notice that "chat with an AI" and "run a command" are, here, one
> mechanism wearing two faces. This is a tool Kernighan and Pike did not have —
> a filter that turns prose into prose — slotted into a pipeline exactly like
> `sort` or `grep`.

## 1.4 What just happened: still just files

The numbered address is not a clever routing scheme. It is, once again, a path on
disk. Open a terminal in the repository and look:

```sh
$ find notebook -maxdepth 4
notebook
notebook/0
notebook/0/a
notebook/0/0
notebook/0/0/a
notebook/0/0/0
notebook/0/0/0/a
notebook/0/0/0/b
```

Every directory is a node in a tree. Inside each node, the file named `a` holds
its text:

```sh
$ cat notebook/0/0/a
What is 2+2?
$ cat notebook/0/0/0/a
4
$ cat notebook/0/0/0/b
created 2026-06-21T14:00:00Z
```

So the URL `/notebook/0/0/0/a` and the answer `4` are the same fact seen from two
sides — once as a web address, once as a file. The directories are numbered
rather than named (`0`, `1`, then `A`, `B`, … when the digits run out) precisely
so that the *next* result always has an obvious place to go. The numbering is a
designed address space, not a substitute for naming things you care about; we
will come back to human-readable names much later. For now, the point is that
nothing was hidden. The conversation you just had is sitting in a directory you
can `grep`, `diff`, edit, delete, and — because it is plain files — commit to
Git and hand to someone else.

This layout has a name of its own, the **Sequential Directory Tree** (SDT), and a
small tool, `sdt`, for tending it. The command that did the filing is a
**Tree-Producing Command** (TPC): a `wash` command whose job is to write new
nodes into such a tree. You do not need either name yet. You have already used
both. That is the order we will keep throughout the book — feel the thing first,
name it second.

## 1.5 Two kinds of file

You have now met everything `wash` is made of, and it comes to two kinds of file.

A file you **read**. Ask for its path and you get its bytes:

```
GET /book/01/index.md        →   the chapter source
GET /notebook/0/0/a          →   "What is 2+2?"
```

A file you **run**. Put it where `wash` looks for commands, and its *name* becomes
a verb you can use in a URL. The command that answered your question lives in the
project's command directory; that is the only reason `wash` treated the first
segment of the POST as something to execute rather than something to fetch.

The difference is not a property of the file's contents — a shell script is just
text — but of *where it sits*. A file on the command path is a verb; the same
file moved out of the command path is just text you can view. We will spend
Chapters 3 and 4 on exactly how `wash` decides, segment by segment, whether a
piece of a URL is a file to read, a command to run, or an argument to a command.
For right now, hold the two-line summary:

- **A name you can read is a file served as content.**
- **A name you can run is a file on the command path.**

Almost everything else in `wash` is a consequence of those two sentences.

## 1.6 GET never changes anything

One promise is worth pulling out before we go further, because it is what makes
it safe to point a browser — a thing that prefetches links, reloads on a whim,
and is driven by a back button — at your own files.

**A GET request never modifies your files.** This is a contract, not a
convention. You can click every link in this book, let the browser reload, share
a URL with a colleague, and nothing on disk changes. Reading is always free of
consequences.

Changing things requires asking for it on purpose, with a different verb:

```sh
curl -X PUT --data 'hello' http://localhost:8080/scratch/greeting.txt
```

That writes `hello` into `scratch/greeting.txt`, creating it if needed. The chat
box you used in §1.3 changed your files too — it accumulated a notebook node — but
notice it did so with a POST, behind a button you chose to press, never on a bare
page load. The division is simple and absolute: GET to look, other verbs to
change. The whole of Chapter 2 is really an elaboration of this one sentence.

> **Try it.** Visit `/scratch/greeting.txt` after the `PUT` above. There is your
> file. Now reload it ten times. It does not change, multiply, or vanish — GET
> just looks.

## 1.7 What we have that 1984 did not

It is worth pausing on why this book can be a *program you run* rather than a
stack of paper, because the answer is also the argument for `wash` itself.

Kernighan and Pike taught the Unix idea with the tools of their day: a terminal,
a line-oriented shell, files, and pipes. The idea was profound and has aged
extraordinarily well — *small programs, composed by streams of text, over a
filesystem that is the source of truth.* What has changed is not the idea but the
equipment around it:

- **The browser** gives us a universal, already-installed interface with
  hypertext, forms, live rendering, and — crucially — *addresses*. A shell
  command vanishes when it scrolls off the screen; a URL can be bookmarked,
  mailed, and clicked a year later. `wash` spends that gift by making the URL the
  composition surface, so a pipeline is a thing you can save by saving a link.
- **Version control** turned "share my environment" from mailing a tape into
  `git clone`. Because every part of a `wash` project — its commands, its
  configuration, its accumulated results — is a plain file, an entire working
  setup travels in a repository. This book is the proof: you got the whole
  environment by cloning it.
- **Language models** are a genuinely new kind of filter: a program that reads
  prose and writes prose. `wash` does not give them a special seat. They are
  commands, subject to the same composition rules as `wc` and `jq`, which means
  the slightly magical box in §1.3 is built from the same parts as everything
  else.
- **Cheap storage** makes it reasonable to keep *everything*. The 1984 instinct
  was to pipe results onward and let them evaporate. `wash` can afford to file
  every result in a tree, so your history of tries is itself a navigable
  artifact.

There is a temptation in all this new equipment, and it is the same one `wash`
exists to resist. The modern browser pulls relentlessly toward opaque
applications — surfaces that *do* a great deal and *reveal* nothing. `wash` keeps
the composition in the open, written in the URL, backed by files you can read.
The through-line from 1984 to here is **transparency**: a command line you can
read is a command line you can trust, change, and reuse. We have better windows
now. The discipline is to keep them clear.

## 1.8 Where we are going

In a single chapter you have started a server, discovered that pages are files,
run a command from the browser, watched it file a result into a tree, and seen
that the whole thing is plain files governed by one safety rule. That is the
entire shape of `wash`. The rest of the book fills it in:

- **Part II** slows down the URL bar and shows exactly how `wash` reads a path —
  what makes a segment a file, a command, or an argument, and the single rule
  (*arity*) that decides where a command's arguments stop and its input begins.
- **Part III** is pipelines: composing commands so that one feeds the next, the
  heart of why `wash` exists.
- **Part IV** is writing your own commands and *promoting* a one-off into a named
  verb you can reuse — the loop this whole book is about.
- **Parts V and VI** return to the tree you already made (SDT and TPC) and to
  drawing whole workflows as graphs you can both *see* and *run* (gripeline).

Type the examples. Click the links. The book is a `wash` app; treat it as one.

## Exercises

1. **Find the source.** This chapter is served from a file. Starting only from
   the address bar, find and view the raw source of the chapter you are reading.
   What URL did you use?

2. **Read your own conversation.** After sending one message in §1.3, write down
   the URLs for (a) your question and (b) the answer, then fetch each directly and
   confirm they match what the page showed.

3. **GET is safe.** Reload the answer page from §1.3 five times. Then look at the
   notebook directory on disk. How many nodes are there? Explain why reloading did
   not add more.

4. **Make a file by hand.** Use `curl -X PUT` to write a short note to
   `/scratch/note.txt`, then view it in the browser. Now view `/scratch/` — what
   do you see, and why?

5. **The LLM is not special (thought experiment).** The box in §1.3 files your
   question and an answer as two nodes. If the command behind the box were `wc`
   instead of an answerer, what would the two nodes contain after you sent a
   paragraph of text? You will be able to actually build this by Part IV.
